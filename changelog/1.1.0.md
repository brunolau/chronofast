# 1.1.0

Four reviewed contributions (thanks, Cvik), every fix verified against native `Temporal`
before merging: reproductions on the previous release, behavior comparisons on the fix, and
the full differential suite on the result. 586 unit tests, 724,360 Temporal checks with zero
disagreements.

> **Versioning.** Two changes below are letter-major if you read strictly: the component
> factories now throw on fields they used to balance, and arithmetic amounts must be
> integers. They ship as a minor, not a major, because the old behavior was never
> documented — it was `Date`-era carryover that produced a *plausible-looking wrong value*,
> which this library's whole design says to reject. If your code passed `Feb 30` to `of()`
> and relied on the roll, it will now throw `RangeError`; that is the intended direction.
> Per the 1.0.2 note, semver applies normally from here, so a future documented-contract
> change like this one would be a major.

### Fixed — parsing and zones

- **A plain value could depend on what was parsed before it.** `parseISO`'s canonical
  fast path (the 24-character `…Z` form) did not reset the shared offset slot, so
  `ChronoPlain.parse('2024-03-15T10:30:00.123Z')` returned `12:30` instead of `10:30` if
  any offset-carrying string had been parsed earlier in the process. Order-dependent
  state on the most common parse path.

- **Sub-minute historical offsets did not round-trip.** The engine already read ICU's
  `GMT-00:44:30` correctly, but formatting truncated to minutes — `Africa/Monrovia` at the
  epoch printed `…-00:44`, which parses back to a different instant — and the parser
  rejected the `±HH:MM:SS` spellings outright. Both fixed: `formatZoned` emits the exact
  `-00:44:30`, and `+00:44:30` / `+004430` parse. Note the deliberate divergence: Temporal
  prints this offset *rounded* (`-00:45`), which does not round-trip through Temporal
  itself; chronofast prints the exact value, which does.

- **Date-only strings with a designator were read two ways.** `parseISO('2000-09-01Z')`
  returned an instant, but `ChronoZoned.parse('2000-09-01Z', tz)` re-read the same string
  as local midnight in `tz` — two hours apart in Bratislava. A designator now means an
  instant on every path, matching the README's own rule.

- **The extreme valid instants threw.** `offsetAt('UTC', 8.64e15)` — the maximum legal
  ECMAScript time value — raised `RangeError` from a cache probe beyond the range, and
  `utcFromWall` did the same for wall readings near either boundary even when the answer
  was representable. All boundary values now resolve; `tryParse` returns `null` when a
  reading genuinely cannot become an instant.

- **`resetZoneCaches()` leaked the locale-formatter caches.** Zone and interval caches
  were dropped; the `Intl.DateTimeFormat` caches were not.

### Fixed — arithmetic

- **No-op calendar arithmetic could move a value by an hour.** `addDays(0)`,
  `addMonths(0)`, `addYears(0)` and `withZoneSameLocal` to the same zone re-resolved the
  unchanged wall clock with `'compatible'`, collapsing the *later* occurrence of an autumn
  fold to the earlier one. A zero date-duration is exact-time addition in Temporal's
  zoned arithmetic, and re-resolving an unchanged reading in its own zone is an identity;
  both now behave that way. `withZoneSameLocal` compares zone ids case-insensitively
  (IANA ids are), and an explicitly passed disambiguation mode still re-resolves.

- **Difference methods wrapped to int32.** `| 0` narrows before it truncates, so
  `secondsUntil` over any interval longer than ~68 years returned a wrong-signed value:

  ```
  1970-01-01 → 2070-01-01   expected  3,155,760,000   returned −1,139,207,296
  ```

  Computing a 96-year-old's age in seconds returned a negative number. All `*Until`
  methods now truncate the full `Number` range, and never return `-0`.

### Fixed and changed — validation (the failing-closed release)

These change observable behavior, in the direction the library's contracts already
claimed:

- **Impossible calendar fields throw instead of balancing.** `ChronoPlain.of(2023, 2, 29)`
  used to become March 1st — matching neither Temporal mode (its `from` *constrains* to
  Feb 28; its constructor throws) nor anything a caller could have intended. The
  factories (`ChronoPlain.of`, `ChronoDate.of`, `ChronoZoned.fromLocal`, `atTime`,
  `toPlain(h, …)`) now throw `RangeError` on fractional, out-of-range, or impossible
  fields, exactly as `new Temporal.PlainDateTime(2023, 2, 29)` does.

- **Fractional and non-finite epoch values are rejected.** `fromEpochMs(0.5)` used to
  produce a "valid" instant that serialized as `…00.000Z`, making 0 and 0.5
  indistinguishable. The instant is an integer count of milliseconds; now enforced at
  every checked entry point, with `isValid` agreeing.

- **Arithmetic amounts must be finite integers**, as Temporal's duration fields must be
  (`addSeconds(0.25)` throws; use `addMilliseconds(250)`), and **arithmetic throws
  instead of returning an unrepresentable value** — `fromEpochMs(8.64e15).addMilliseconds(1)`
  raises `InvalidInstantError`, like Temporal.

- **The parser rejects instants outside the ECMAScript time range.**
  `ChronoInstant.parse('+275760-09-13T00:00:00.001Z')` used to return a value past the
  representable maximum with no error; `Temporal.Instant.from` throws, and so does
  chronofast now. Wall-clock and zoned parsing keep Temporal's one-day-padded
  intermediate range (`ISODateTimeWithinLimits`), so a boundary instant is still
  reachable through every zone offset — `+275760-09-13T12:00` resolves in `Etc/GMT-12`
  and throws in `UTC`, same as Temporal.

- **`ChronoDate` covers Temporal's complete `PlainDate` range**, `-271821-04-19` through
  `+275760-09-13`. The first day used to throw on parse; the wider range means a
  `ChronoDate` at the extremes cannot always become a `ChronoPlain` (whose wall range is
  the ECMAScript one), so `toPlain()` and `toLocaleString()` throw there — stated in the
  README's limitations.

- **The class constructors are documented as what they always were**: unchecked
  low-level entry points for already-validated branded values. `parse`, `of`, `from*` are
  the checked doors. This is what keeps ordinary arithmetic a pair of comparisons.

### Performance

Validation costs a measurable, deliberate ~0.5–2 ns per checked class call (paired
fresh-process A/B against 1.0.2; `addMilliseconds` +0.61 ns, zoned `addDays` +5 ns,
serializers +1–2 ns, raw-layer arithmetic unchanged, parsers unchanged). The minified
browser bundle grows from 7.50 to 8.22 kB gzipped — the price of the checks themselves;
the raw layer, which hot loops should use, is unchanged.
